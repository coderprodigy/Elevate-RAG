# Gate G1: first end-to-end run with real models (2026-11-27)

**Verdict: the pipeline passes G1; the $0 small-model setup does not produce research-grade
numbers.** Every stage ran on real data with real models, end to end, with costs, logs, resume
and reporting working. The run also showed that a 3B judge is unreliable and a 3B extractor
builds too sparse a graph. Do not cite these accuracies as findings.

## Setup

| | |
|---|---|
| Data | `hotpotqa_g1`: 20 HotpotQA distractor questions (all `hard`), 200 paragraphs, seed 13 |
| Generator / extractor / keywords | Qwen2.5-3B-Instruct (Ollama, 8192-token context, seed 0) |
| Judge | Llama-3.2-3B (different family from the generator) |
| Embedder / reranker | BAAI/bge-small-en-v1.5 / BAAI/bge-reranker-v2-m3 (pinned revisions) |
| Storage | exact vector search + NetworkX (in-process; Docker was unavailable) |
| Config | `configs/pipelines/local_free.yaml`, `configs/experiments/G1_smoke_local.yaml` |
| Cost | $0.00 (all local); graph build 91 min, 6 variants 36 min on an Apple-silicon laptop |

Paired comparison with V4 (exact McNemar, Holm-corrected): **no variant differs significantly.**
mix vs V4: +0.25, bootstrap CI [0.06, 0.44], p = 0.062, p_holm = 0.31.

R1 routed 9 questions to vector, 7 to local and 4 to mix.

## Findings

1. **The 3B judge is not trustworthy.** Across variants it accepted 3–6 responses per variant
   that do not contain the gold answer. Of the six for `mix`, five are plainly wrong (e.g. "James
   Cummins" for *Jarome Iginla*, "Paride ed Elena" for *Alceste*); only "Manhattan" for *New York
   City* is defensible. By the judge-free check, mix's lead over V4 shrinks from +5 to −1
   questions. A stronger judge is needed, and judge-based numbers count only after the
   automated judge validation (GroUSE calibration + agreement of two judges, D-36).
2. **The 3B extractor builds a sparse graph.** 1,026 entities but only 355 relations; 616
   entities (60 %) have no relation. LightRAG discarded 1,263 malformed relation lines.
   Answer-entity coverage was 4/4 on the dev questions (passes G3's ≥ 60 %, but n = 4). Graph
   modes are under-powered with this extractor, so these numbers say little about RQ2.
3. **Small-model keyword extraction sometimes returns nothing** ("low_level_keywords is
   empty"), so some graph-mode queries ran with little graph context.
4. **Retrieval is not the bottleneck here**: recall@10 is 0.90–1.00 because each HotpotQA
   distractor question comes with only 10 candidate paragraphs. Answer quality is limited by
   the 3B generator (EM 0.05–0.15).

## Defects found by this run (all fixed, regression-tested)

| Defect | Fix |
|---|---|
| FAISS + PyTorch in one process abort on macOS (duplicate OpenMP runtime) | refused with a clear error (`guard_openmp`) |
| Ollama's default 4096-token context silently truncates long prompts | 8192 required and documented in `local_free.yaml`; truncation monitored in the Ollama log |
| 3B extractor repetition loops (66 lines, 17 unique) overflow the context | new `lightrag.extract_max_tokens` setting (part of the index identity); gleaning off for small models |
| Latency of variants that reuse cached LLM calls reported as ~0 s | latency computed only over queries without cached LLM calls; `cache_hit_rate` reported |
| Deprecated `merge_strategy` argument warned on every entity merge | removed (LightRAG's defaults are identical) |
| `elevate-rag env` crashed when the Docker daemon hung | reports `docker_daemon: false` |

## Follow-up

The same 20 questions were re-run with Qwen2.5-7B + Llama-3.1-8B: see
[`../g1_7b/G1_7B_RESULTS.md`](../g1_7b/G1_7B_RESULTS.md). With the better judge mix's lead
disappears (0.55 vs V4 0.50, not significant), confirming finding 1. The G3 coverage matcher was
later made robust to space-stripped entity names; this graph's result (4/4) is unchanged by it.
