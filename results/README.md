repository. Nothing is hand-entered. Raw per-question records live in `runs/` (git-ignored) and
are regenerated by re-running the command; see [docs/RUNNING.md](../docs/RUNNING.md).

## How to read them

* **These are not the plan's research results.** E1–E6 and A1–A4 have not been run: they need
  GPU time or an API budget. G1 runs exist to prove the pipeline and to find problems cheaply
  before that spend; the defects each one surfaced are listed in its write-up.
* **Primary metrics are exact match and token F1**, the benchmarks' official judge-free answer
  metrics. LLM-judge accuracy counts only when the run record says
  `judge_validation.status: validated`: both judges passed GroUSE calibration and agreed with
  κ ≥ 0.6 on that run's answers (DECISIONS D-36). **No committed run is validated yet**: the G1
  runs had one judge each, and the 8B judge scored 0.78 on GroUSE.
* Every accuracy comes with a 95 % bootstrap CI; paired differences use exact McNemar with Holm
  correction, on EM and on the judge verdict. With n = 20 one question is 5 points, so only very
  large differences can be significant.
* Latency is reported only over queries whose LLM calls actually ran (not served from cache);
  `n/a` means a variant reused cached calls from an earlier variant.

## Tracing a number back

1. Find the run in [`runs/INDEX.csv`](runs/INDEX.csv) and open its record
   `runs/<experiment>/<run_id>.json`.
2. The record names the code (`code.git_commit`; `git_from_run: false` marks runs recorded
   after the fact, as for G1, whose commit is the one that wrote the record), the configuration
   (`config_hash`, `variant`, `split`, `limit`), the data (`dataset_version`) and every model
   with its revision.
3. Re-run: check out the commit, prepare the dataset and run the same spec with the same
   pipeline; the run id (which embeds the config hash) must match. The raw predictions are in
   `$ELEVATE_RUNS_DIR/<raw_run_dir>` on the machine that ran it.
